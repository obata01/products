# コーディング規約

## コーディング
- 冗長なコードは避け、単一責任の原則に従ってクラスや関数に適切に分割する.
- DRY原則に従い類似コードは可能な限り共通化する.
- ruffによるlinterの使用を必須とする.
- if文の多用は避け、クラス化・辞書によるマッピングなどを検討する.
- PYTHONPATHに`/app`を追加しているため、importはsrcからの絶対参照とする. ※ただしcomponents配下は相対パス.

## Docstring

- 全てのクラスとパブリックメソッドに Google Style の Docstring を記述する.
- Docstringは日本語で記載する.
- 説明は簡潔にしてドットで終えること.
- Docstring側へのデータ型の記載は不要（コード側の型ヒントで十分）.
- 必要に応じて Raises セクションも追記する.

```python
def sample_function(arg1: int, arg2: str) -> bool:
    """説明は簡潔にしてドットで終えること.

    Args:
        arg1: 引数1
        arg2: 引数2

    Returns:
        戻り値

    Note:
        - 必要に応じてNoteに補足を記載.
    """
    return True
```

## コメントポリシー

- テストコードを除くソースコードでは、コメントの使用を最小限にする.
- 変数名・関数名・docstring・コードの構造で意図を伝えることを優先する.
- それでも読み手に伝わりにくい箇所にのみコメントを残す.
- セクション区切りとして視認性を高める目的のコメントは許可する.
- `# noqa` 等のリント制御コメントはこのルールの対象外.
- コード側に不要なコメントアウトを入れない.
