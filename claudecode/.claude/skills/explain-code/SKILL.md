# explain-code

指定されたコードを初見の読み手でも理解できるレベルまで噛み砕いた補足説明ドキュメントを生成するスキル.

## 実行手順

### 1. 対象コードの特定

ユーザーの指示から解説対象を特定する.

- ファイルパス・関数名・クラス名・行範囲などが指定されていれば、その範囲を対象とする.
- 範囲が曖昧な場合は、ユーザーに対象範囲を確認する.
- IDEで開かれているファイル（`ide_opened_file`）や選択範囲（`ide_selection`）がある場合は、そこを暗黙の対象候補とする.

### 2. コード本体・依存先の読み込み

- `Read` で対象コードを読む.
- 対象が依存する自作モジュール（import先）も必要に応じて `Read` / `Grep` で確認し、呼び出し関係を把握する.
- 外部ライブラリの挙動が論点になる箇所は、公式ドキュメント等を `WebFetch` / `WebSearch` で調べて裏取りする（推測で書かない）.

### 3. 解説ドキュメントの作成

以下の構成でMarkdownを生成する. 日本語で記載する.

```markdown
# <対象コード名 or ファイル名> 解説

## 概要
- このコードが何をするものか（2〜4行程度）.
- どのレイヤー（components / application / common など）に属し、何を責務とするか.

## 依存関係
- import している主要モジュール・外部ライブラリと、それぞれの役割.
- 呼び出し元・呼び出し先の関係（分かる範囲で）.

## 行毎の処理解説
<対象コードを適切な単位（関数・ブロック・数行）で区切り、それぞれに対して以下を記載>
- そのブロックの目的.
- 使用している関数・クラス・構文の意味.
- 外部ライブラリを利用している場合は、そのライブラリの仕様・引数の意味・戻り値の形・副作用などを明記する.
- 初見で引っかかりやすい箇所（暗黙の挙動・型変換・非同期・例外伝播など）を補足する.

## 仕様・設計上のポイント
- 設計意図、選択理由、代替案と比較した場合のトレードオフ.
- 注意点・既知の制約・落とし穴.

## 参考
- 参照した公式ドキュメント・Issue・関連ファイルへのリンク.
```

### 4. 出力先の決定とファイル出力

- ユーザーから出力先が指定されていれば、そのパスに出力する.
- 指定がなければ `documents/memo/` 配下に出力する.
- 出力ディレクトリが存在しない場合は `Bash` で `mkdir -p` する.
- ファイル名は `<対象コードを表す簡潔な名前>_explain.md` を既定とする（例: `claude_code_node_explain.md`）. ユーザー指定があればそれに従う.
- 既存ファイルがある場合は、上書きしてよいかユーザーに確認する.

### 5. 完了報告

- 出力ファイルへのリンク（markdownリンク形式）を提示する.
- 解説した範囲と、確認が取れずに推測を含めた箇所があればそれを明示する.

## 品質ガイドライン

- **推測と事実を区別する**: 外部ライブラリの挙動は一次情報で裏取りし、裏取りできなかった箇所は「要確認」と明記する.
- **初見の読み手を想定する**: プロジェクト固有の略語・暗黙の前提はすべて言葉にする.
- **コードの引用は最小限に**: 全文コピペではなく、該当行を引用しつつ「なぜそう書くのか」に紙面を割く.
- **WHYに比重を置く**: WHATはコードを読めば分かる. このドキュメントの価値はWHYの明文化にある.
- **プロジェクト規約を尊重する**: `.claude/rules/` 配下のコーディング規約・構成方針と矛盾する説明はしない.
